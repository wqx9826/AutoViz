# AutoViz 通信协议设计原则

本文只设计未来通信接口的原则，不实现协议、不添加 `.proto` 文件、不引入通信框架，也不改变当前 ROS2 单体程序。

## 通信目标

未来协议需要支持：

- Linux Server 侧部署 ROS2、仿真或日志适配器。
- Windows 及其他平台运行 Client。
- Client 在没有 ROS2 安装、ROS2 middleware 或 `custom_msgs` 的情况下正常启动和显示。
- 同一个 Client API 消费实时数据、仿真数据和日志回放数据。
- 允许协议长期演进，并能明确处理版本、能力、时间戳、数据有效性和超时。

通信协议的边界应放在“标准化后的 AutoViz 数据”上，而不是放在 ROS2 topic 或具体 middleware 上。

## 数据格式选择

| 格式 | 优点 | 限制 | 适合位置 |
| --- | --- | --- | --- |
| JSON | 可读、易调试、工具丰富、临时接口成本低 | 体积较大、类型约束弱、解析开销和兼容约束容易被推迟 | 调试、诊断、样例或人工检查 |
| protobuf | 有 schema、跨语言、体积较小、编码稳定、支持字段演进 | 需要维护 schema 和生成代码，调试时不如 JSON 直观 | 主数据接口，推荐 |
| 自定义 binary | 可以针对特定链路压缩和优化 | 语义不透明、兼容性和工具链成本高、容易与实现绑定 | 经过测量后仍有明确性能瓶颈的专用链路 |

### 推荐结论

推荐 **protobuf 作为数据描述格式**。protobuf 负责定义跨平台的数据结构、字段类型、可选字段和版本演进规则；它本身不是传输层。第一阶段的传输组合建议为 **protobuf + TCP**。

JSON 可以作为开发期诊断或导出格式保留，但不应成为实时主链路的长期契约。自定义 binary 暂不作为第一阶段方案。

## 通信方式分析

| 方式 | 优点 | 限制 | 当前建议 |
| --- | --- | --- | --- |
| TCP | 有序、可靠、连接语义清晰，适合完整快照和状态流 | 有重传和队头阻塞，必须处理断线、缓冲和背压 | 第一阶段推荐 |
| UDP | 延迟低、可容忍丢包，适合高频且可丢弃的瞬时数据 | 无可靠性、无序和无连接，需要自行处理发现、重排和丢包 | 后续对明确的高频数据按需评估 |
| WebSocket | 便于浏览器、代理和 Web 生态接入，可承载文本或 binary frame | 增加 WebSocket 层和部署约束，原生 Qt Client 第一阶段不需要 | 不是第一阶段默认方案 |

### 第一阶段推荐

第一阶段采用 **protobuf + TCP** 的设计方向：TCP 提供可靠有序的连接，protobuf 提供跨语言的数据描述和版本演进。具体 framing、握手、重连和压缩细节应在 `feature/client-server` 分支获得人工确认后再设计和实现。

## Server API 设计原则

### 1. API 面向标准化数据

Server 对外提供车辆状态、路径、障碍物、控制、任务、Topic/来源状态和运行模式等 AutoViz 标准语义。API 不暴露 ROS2 msg 类型、ROS2 header、topic 名称作为 Client 的业务依赖。

### 2. Client 不关心数据来源

Client 不关心：

- ROS2 是否存在；
- 数据来自真实车辆、simulation 还是 log；
- Server 使用了哪种 middleware；
- Server 内部有多少个 ROS2 topic 或 Adapter。

这些信息如果对诊断有用，应作为来源元数据或能力信息以稳定字段提供，而不是让 Client 解析来源专有结构。

### 3. Server 提供稳定接口

Server API 至少应能表达以下概念：

- 获取当前完整快照。
- 订阅持续更新的数据流。
- 获取数据源、能力、协议版本和 schema 版本。
- 获取每个通道的时间戳、序列号、有效性、新鲜度和错误状态。
- 表达空数据、部分数据和字段未支持，不能用“保留上一帧”代替无数据。

初期可以以完整快照为主要同步单位；只有在实际带宽或刷新性能证明需要时，再增加增量更新。无论采用快照还是增量，Client 都应能判断一帧数据是否完整、是否过期以及是否属于同一任务/会话。

### 4. 版本、单位和坐标必须显式

- 协议版本和能力协商要能区分兼容与不兼容字段。
- 时间戳、序列号、来源标识和 frame/坐标系不能依赖隐含约定。
- 角度、角速度、速度、深度等单位必须在 schema 或明确的协议约定中固定。
- 当前 UI 的角度显示规则仍然适用：显示端使用度和 `°/s`，内部计算可以使用弧度，但转换点必须明确。

### 5. Adapter 与 API 解耦

Server 内部使用 Adapter 模式：

```text
ROS Adapter       Simulation Adapter       Log Adapter
      \                    |                    /
       +------ 标准化数据模型 / 缓存 ------+
                         |
                    Server API
                         |
                      Client
```

每个 Adapter 负责采集和转换；缓存、数据新鲜度和 API 输出使用统一规则。替换来源时不应要求 Client 改动。

## 当前未决事项

以下事项属于未来设计阶段，不在当前 `main` 分支实现：

- protobuf schema 的具体消息层次和字段编号；
- TCP 消息 framing、握手、重连、心跳和背压策略；
- 完整快照与增量更新的边界；
- 认证、权限、压缩和多 Client 会话管理；
- ROS2、仿真和日志 Adapter 的统一时间语义。

任何上述实现都必须先获得人工确认，并在 `feature/client-server` 分支进行。
